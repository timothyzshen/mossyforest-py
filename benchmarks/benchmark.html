BonsaiForest — Speed Benchmark

Standalone Python package configurations vs. the R reticulate backend

What this benchmarks

This document compares wall-clock runtime of bonsaiforest.bf() across:

  1. Configurations of the standalone Python package — sequential vs. parallel (num_processors), with/without Numba, and the cost of materializing the (lazy) TreeSHAP interaction matrix.
  2. The R package’s reticulate path — sf(..., backend="python") in R, which calls inst/python/sf_python_backend.py through reticulate.

All runs use an identical synthetic dataset (300 samples × 64 features: 4 correlated modules of 12 features + 16 independent noise features), the same seed, and the same screen/select parameters, so the numbers are directly comparable.

NoteTwo important caveats
  • shap_backend="fasttreeshap" is not benchmarked here. It pins shap<0.46 → numpy<2, a stack with no wheels for Python ≥3.12, so it cannot be installed on this machine’s Python 3.13. The code path exists and works on Python ≤3.11; on a modern stack keep the default "shap".
  • The R path uses a different Python environment (reticulate’s r-reticulate venv) than the standalone package (system python3). Its sklearn/shap versions differ, so its stable-feature count can differ slightly. Treat the R numbers as “the realistic R-via-reticulate experience,” not a same-stack apples-to-apples SHAP comparison.

Screening cache — tuning-sweep speedup

Phase 1 (screening) depends only on X, y, module membership, screen_params, and the seed — not on select_params. A tuning sweep over pi_thr (or CV) therefore recomputes identical screening every run. screen_cache=True caches it so only the first run pays for Phase 1.

no_cache, cached, speedup = run_cache_sweep(X, y, mm)
print(f"4-value pi_thr sweep:")
print(f"  no cache     : {no_cache:6.1f}s")
print(f"  screen_cache : {cached:6.1f}s   ({speedup:.2f}x faster)")
4-value pi_thr sweep:
  no cache     :   57.6s
  screen_cache :   45.8s   (1.26x faster)

The win grows with the number of sweep points and with datasets where screening is a larger share of runtime (more/larger modules).

R ↔︎ Python parity

Separately from speed, parity_check.py verifies the two implementations agree. With R’s reticulate pinned to the same Python interpreter (so only algorithmic differences remain), the measured agreement on identical data/seed was:

  • selected-set Jaccard = 0.944 (17/18 features shared)
  • mean |Δ stability-frequency| = 0.004, max 0.067

The lone difference is a single borderline independent feature at the selection threshold, flipped by float32 (package) vs float64 (R backend) — a sub-epsilon effect, not an algorithmic divergence. Run it with:

python benchmarks/parity_check.py

How to read this

  • Standalone Python ≈ 1.6× faster than R-via-reticulate (11.3 s vs 18.1 s) on identical data — from float32, the parallel bootstrap loop, and avoiding reticulate’s R↔︎Python marshalling. The R backend’s bootstrap loop is still sequential, so extra num_processors barely helps it (18.1 → 16.9 s).

  • Parallelism (num_processors) gives a modest ~1.14× here because the dataset is small (sub-second RF fits, so thread overhead dominates). The speedup grows with n, n_features, n_boots, and module count — scale the dataset in make_data() to see it widen. Determinism holds regardless of worker count (see tests/test_optimizations.py::test_parallel_matches_sequential).

  • Numba is marginal (~0.97–1.0×): the JIT’d mean‖SHAP‖ reduction is a tiny slice of runtime next to TreeSHAP itself. It only helps at large n_samples, and even then modestly. Left off by default.

  • The interaction matrix costs ~1.5 s (9.97 → 11.55 s) — which is exactly why it is computed lazily. You pay it only when you access result.interaction_matrix / detect_interaction() / plot_potential_interactions(), not on every fit().
